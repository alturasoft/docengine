1. Visión General

DocEngine es una plataforma de servicios de alto rendimiento orientada a la digitalización, extracción estructurada, clasificación y consulta conversacional (RAG) de pólizas de seguros en el mercado boliviano.

El motor procesa documentos PDF complejos —tanto nativos digitales como escaneados mediante OCR—, estandariza su estructura visual en representaciones Markdown y esquemas JSON jerárquicos, fragmenta el contenido bajo una estrategia Parent-Child, genera representaciones vectoriales densas de 1024 dimensiones con el modelo local BAAI/bge-m3, y consolida la información tanto de forma relacional como vectorial en PostgreSQL con la extensión pgvector.

Principios de Arquitectura e Integración

  • Versionado Estricto: Todos los endpoints de negocio se exponen bajo el prefijo /api/v1/, asegurando una evolución predecible y compatibilidad hacia atrás con los sistemas cliente.
  • Formatos Estandarizados: La comunicación estructurada utiliza exclusivamente JSON codificado en UTF-8, mientras que la recepción de archivos binarios se efectúa mediante multipart/form-data.
  • Idempotencia Nativa: Cada ingesta calcula el hash criptográfico SHA-256 del documento. Si el archivo ya fue procesado previamente, el sistema evita cómputos redundantes y previene la duplicación de fragmentos vectoriales.
  • Arquitectura de Sobres (Policy Envelopes): Los documentos asociados a una misma póliza no se gestionan de forma aislada, sino que se integran en "sobres de póliza", agrupando coherentemente carátulas, condiciones generales, condiciones particulares, liquidaciones de pago y anexos.
  • Aislamiento y Trazabilidad de Clientes (id_cliente / nombre_cliente): Toda operación de ingesta, indexación y consulta puede segmentarse por el identificador de cliente (id_cliente) y su nombre o denominación social (nombre_cliente), garantizando estricta confidencialidad, separación lógica y trazabilidad personalizada.

2. Entornos y Direcciones Base

La API de DocEngine se despliega mediante una arquitectura desacoplada, facilitando su consumo en distintos puntos de enlace según la fase del ciclo de vida del software. Las direcciones de host y puertos definitivos se establecen conforme a la infraestructura y configuración de red de cada despliegue.

Entorno URL Base de Endpoints Documentación Interactiva (Swagger) Propósito Operativo

Documentación Interactiva y Especificación OpenAPI
DocEngine publica el esquema OpenAPI v3 estándar en la ruta /openapi.json e incluye interfaces gráficas interactivas para exploración y pruebas en /docs (Swagger UI) y /redoc (ReDoc). La especificación se mantiene sincronizada con el repositorio en docs/openapi.json bajo la directiva formal de versionado docs/API_VERSIONING_POLICY.md.

3. Autenticación y Autorización (RBAC)

DocEngine incorpora un esquema de seguridad basado en cabeceras de API Key (X-API-Key), complementado con control de acceso basado en roles (RBAC). El sistema admite operación abierta únicamente en redes internas o entornos de desarrollo local; para entornos productivos y de homologación, la autenticación estricta se activa mediante la variable de entorno DOCENGINE_SECURITY_ENABLED=true.

Cabecera HTTP de Autenticación

X-API-Key: <TU_API_KEY_SECRETA>

Matriz de Perfiles y Roles de Usuario

Rol Alcance de Permisos Endpoints Autorizados
readonly Consulta y lectura POST /api/v1/query/search, POST /api/v1/query, GET /api/v1/policies/* (incluyendo esquemas estructurados) y GET /api/v1/health/*.
writer Lectura e ingesta documental Habilita todos los permisos de readonly más la carga documental en POST /api/v1/extract/* y el seguimiento de trabajos en GET /api/v1/extract/jobs/*.
admin Administración integral Comprende la totalidad de operaciones previas y autoriza la eliminación controlada de documentos (DELETE /api/v1/policies/{policy_id}) y de sobres completos (DELETE /api/v1/policies/envelopes/{envelope_id}).

4. Estándar Global de Errores y Respuestas

El diseño de la API se apega a los lineamientos RESTful y las convenciones estándar de FastAPI, asegurando una estructura uniforme y predecible en todas las respuestas de excepción mediante el esquema ErrorDetailSchema.

Estructura Estándar de Respuesta de Error (ErrorDetailSchema)

{
  "detail": "Descripción precisa y contextualizada de la causa del error o de la validación",
  "error_code": "INVALID_PAGE_COUNT",
  "timestamp": "2026-10-14T18:00:00Z"
}

Catálogo de Códigos de Estado HTTP

Código HTTP Estado Contexto de Aplicación en DocEngine
200 OK Procesamiento Exitoso La solicitud se ejecutó satisfactoriamente y se retorna la carga útil solicitada en el cuerpo de la respuesta.
202 Accepted Aceptado para Procesamiento Asíncrono La carga fue validada e incorporada a la cola de procesamiento en segundo plano; se suministra un job_id para el seguimiento del trabajo.
400 Bad Request Solicitud Inválida Parámetros ausentes o incorrectos, tipo de archivo no admitido o documento PDF con inconsistencias estructurales.
401 Unauthorized No Autenticado Omisión de la cabecera X-API-Key o clave de acceso no reconocida por el sistema.
403 Forbidden Acceso Restringido La credencial proporcionada carece de privilegios suficientes para la acción requerida (por ejemplo, rol readonly ejecutando operaciones de borrado).
404 Not Found Recurso No Encontrado El sobre (envelope_id), documento (policy_id) o trabajo (job_id) especificado no existe en el registro.
413 Content Too Large Archivo Excede Capacidad El tamaño del archivo cargado supera el límite técnico predeterminado (200 MB).
422 Unprocessable Content Validación Semántica o Límite de Extensión Discrepancia en la validación del esquema Pydantic, o el archivo supera el umbral máximo permitido de 500 páginas.
500 Internal Error Error Interno del Servidor Excepción no controlada originada en el motor de extracción Docling o en el gestor de base de datos PostgreSQL.
503 Service Unavailable Servicio no Disponible Indisponibilidad momentánea o etapa de calentamiento/inicialización del motor vectorial o del servicio de base de datos.

5. Parámetros de Consulta y Filtros Avanzados

Los endpoints de recuperación semántica (/query/search) y de gestión documental admiten criterios de búsqueda estructurados y combinables mediante el esquema SearchFiltersSchema:

Parámetro Tipo de Dato Definición y Alcance Ejemplo
id_cliente string Aislamiento estricto multi-inquilino por titular de póliza (Carnet de Identidad o NIT). Requerido obligatoriamente en la ingesta documental. "1020415021"
nombre_cliente string Nombre completo, razón social o denominación del titular/tomador de la póliza. Parámetro complementario situado jerárquicamente tras el id_cliente para enriquecimiento contextual, auditoría y búsquedas semánticas. "Minera San Cristóbal S.A."
policy_id string (UUID) Identificador unívoco del documento en el repositorio central (formato canónico UUID de 36 caracteres). "4b684531-10df-4f40-84cf-8d9633e6c0c2"
numero_poliza string Número o código contractual asignado a la póliza por la aseguradora. Debe distinguirse del policy_id interno. "POL-2024-9988"
company_sigla string Sigla canónica de la entidad aseguradora según el catálogo oficial de 18 compañías (GET /api/v1/catalogs/companies). Admite el alias sigla_aseguradora por retrocompatibilidad. "BISA", "CRE", "LBC"
ramo string Ramo técnico normalizado conforme a la codificación de la APS (GET /api/v1/catalogs/ramos). "AUTOMOTOR", "INCENDIO"
tipo_documento string Clasificación tipológica del documento según catálogo normativo (GET /api/v1/catalogs/document-types): POLIZA, CONDICIONADO_GENERAL, etc. "CONDICIONADO_GENERAL"
vigencia_fecha string (ISO) Filtra documentos cuya vigencia contractual comprenda la fecha indicada (formato YYYY-MM-DD). "2024-06-15"

6. Catálogo Detallado de Endpoints

6.1 Módulo de Ingesta y Extracción Documental (Extraction)

POST /api/v1/extract/file

Propósito: Carga un archivo binario PDF para su extracción estructural, segmentación (chunking) y generación de incrustaciones vectoriales. Permite ejecución síncrona directa o diferida en segundo plano activando el parámetro async_mode=true.

Content-Type: multipart/form-data

Campo de Formulario Tipo de Dato Obligatorio Descripción Técnica
file Binary (PDF) Sí Documento PDF a procesar (máximo 200 MB y 500 páginas).
id_cliente string Sí Identificador de cliente (Carnet de Identidad o NIT) requerido para la segmentación y aislamiento multi-inquilino. No puede enviarse vacío.
nombre_cliente string No Nombre completo o razón social del cliente / tomador. Parámetro normal situado jerárquicamente tras el id_cliente. En caso de no suministrarse, el pipeline RAG intentará inferirlo de manera inteligente a partir del tomador o asegurado identificado en las cláusulas de la póliza.
company_sigla string No Sigla oficial de la aseguradora según catálogo (ej. BISA, CRE, LBC). Admite el alias sigla_aseguradora.
numero_poliza string No Número comercial de la póliza para indexación y vinculación en su sobre correspondiente.
ramo string No Ramo de seguro asociado a la póliza (ej. AUTOMOTOR, TODO_RIESGO).
tipo_documento string No Clasificación del documento (ej. POLIZA, CONDICIONADO_GENERAL).
async_mode boolean No (def: false) Si se establece en true, encola la tarea en segundo plano y retorna de inmediato el código 202 Accepted junto con el job_id.

Ejemplo de Respuesta Asíncrona (202 Accepted):

6.2 Módulo de Catálogos Normativos Maestros (Catalogs)

DocEngine provee endpoints de consulta para catálogos estandarizados de aseguradoras, ramos y tipologías documentales, garantizando la consistencia terminológica en las integraciones externas:

GET /api/v1/catalogs/companies

Propósito: Retorna el catálogo oficial de las 18 entidades aseguradoras supervisadas en Bolivia, detallando su identificador numérico (id), razón social (nombre), sigla canónica (sigla, ej. BISA, CRE, LBC, ALI-SEG) y sigla previa (sigla_anterior).

GET /api/v1/catalogs/document-types

Propósito: Retorna la relación de tipologías documentales admitidas en la plataforma (POLIZA, CONDICIONADO_GENERAL, CONDICIONADO_PARTICULAR, ANEXO, LIQUIDACION_PAGOS, entre otras).

GET /api/v1/catalogs/ramos

Propósito: Retorna el catálogo lineal de ramos de seguros autorizados según la codificación de la APS. La vista estructurada por categorías de ramo se encuentra en GET /api/v1/catalogs/ramos/grouped.

6.5 Módulo de Sistema y Monitoreo (System & Health)

GET /api/v1/health

Propósito: Verificación de latido operativo básico (liveness probe). Retorna {"status": "ok"} para validar la disponibilidad del servicio.

GET /api/v1/health/system

Propósito: Diagnóstico técnico del entorno: versión activa de DocEngine, estado del motor de extracción Docling, conectividad con PostgreSQL y modelos vectoriales cargados en memoria.

7. Límites Técnicos por Archivo y Rendimiento

Con el fin de preservar la estabilidad operativa del entorno y prevenir la saturación de recursos por archivos anómalos o de volumen excesivo, DocEngine ejecuta validaciones deterministas antes de procesar cada documento:

Criterio Límite Operativo Código de Error Mecanismo de Control
Tamaño de Archivo 200 MB por documento 413 Content Too Large Rechazo inmediato antes de transferir el flujo binario a la memoria principal.
Extensión en Páginas 500 páginas por documento 422 Unprocessable Content Inspección de metadatos estructurales previa al inicio de la extracción Docling.
Formato de Archivo Únicamente application/pdf 400 Bad Request Validación de la firma binaria de cabecera (magic bytes) del estándar PDF.
Tratamiento de Documentos de Gran Extensión
Aquellos documentos que excedan el límite de 500 páginas deben segmentarse previo a la ingesta en fascículos lógicos (por ejemplo, carátula, condiciones particulares y anexos en archivos independientes) o canalizarse a través del modo asíncrono configurando el parámetro max_pages_per_file en PerformanceConfig, evitando la desconexión por tiempo de espera (timeout) en clientes HTTP síncronos.

8. Procesamiento Asíncrono, Idempotencia y Condicionados Generales

Condicionados Generales Compartidos

En la práctica aseguradora de Bolivia, un condicionado general suele regir de manera uniforme para múltiples pólizas de un mismo ramo. DocEngine permite registrar el condicionado general una sola vez con tipo_documento="CONDICIONADO_GENERAL". Posteriormente, las consultas RAG y los agentes externos pueden recuperar los fragmentos correspondientes aplicando el filtro ramo, eliminando la necesidad de duplicar archivos físicos o recomputar vectores para cada póliza.

Ciclo de Vida de los Trabajos (Jobs)

Estado Descripción Operativa
PENDING Documento recibido y validado; registrado en la cola de procesamiento en segundo plano.
PROCESSING Extracción estructural con Docling, segmentación semántica y generación de vectores BGE-M3 en curso.
COMPLETED Procesamiento completado; datos estructurados e incrustaciones vectoriales persistidos exitosamente en PostgreSQL.
FAILED Interrupción controlada del pipeline ante una excepción; incluye la traza descriptiva en error_message.
Guía Rápida de Integración para Desarrolladores
Flujo de trabajo recomendado para agentes de IA y sistemas de gestión (ERP/Core):
  1. Búsqueda contextual para LLM externo: Invocar POST /api/v1/query/search con la consulta en lenguaje natural y los filtros requeridos.
  2. Consulta de datos contractuales estructurados: Obtener coberturas, límites y deducibles mediante GET /api/v1/policies/{policy_id}/structured.
  3. Ingesta de documentos voluminosos: Cargar mediante POST /api/v1/extract/file?async_mode=true y consultar el progreso a través de GET /api/v1/extract/jobs/{job_id}.
  4. Sustitución de anexos o condicionados erróneos: Eliminar el documento específico con DELETE /api/v1/policies/{policy_id} y cargar el reemplazo sin necesidad de recrear el sobre completo.
