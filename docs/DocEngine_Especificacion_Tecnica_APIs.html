1. Visión General

DocEngine es una plataforma de servicios de alto rendimiento diseñada para la digitalización, extracción estructurada, clasificación y consulta conversacional (RAG) de pólizas de seguro en Bolivia.

El sistema procesa documentos PDF complejos (nativos o escaneados con OCR), normaliza la estructura visual a Markdown estructurado y JSON, fragmenta el contenido en jerarquías Parent-Child, genera representaciones vectoriales densas de 1024 dimensiones utilizando el modelo local BAAI/bge-m3, y almacena la información tanto relacional como vectorialmente en PostgreSQL con la extensión pgvector.

Principios Clave de la API

  • Versionado Estricto: Todos los endpoints de negocio están bajo la ruta base /api/v1/, garantizando evolución controlada y compatibilidad hacia atrás.
  • Formato Estándar: Todas las peticiones y respuestas estructuradas utilizan JSON codificado en UTF-8 (salvo la carga de archivos binarios vía multipart/form-data).
  • Idempotencia Nativa: Toda ingesta documental verifica el hash criptográfico SHA-256 del archivo; si el documento ya fue procesado, no se reprocesa innecesariamente, evitando costos de cómputo y duplicación de vectores.
  • Arquitectura de Sobres (Policy Envelopes): Los documentos no existen aislados; se agrupan lógicamente en "sobres" que representan la póliza completa (agrupando carátula, condicionados generales, condicionados particulares, liquidaciones y anexos).
  • Aislamiento Multi-Inquilino (id_cliente): Cada operación de ingesta y consulta puede aislarse por identificador de cliente, garantizando la privacidad de los datos.

2. Entornos y URLs Base

La API se despliega de forma desacoplada y puede consumirse a través de los siguientes endpoints base según el ciclo de vida del software:

Entorno URL Base de Endpoints Documentación Swagger UI Propósito
Desarrollo Local http://localhost:8000/api/v1 http://localhost:8000/docs Pruebas locales, ejecución directa con Uvicorn.
Staging / Pruebas http://192.168.1.50:8000/api/v1 http://192.168.1.50:8000/docs Validación de integración y QA con clientes internos.
Producción https://docengine.altura.bo/api/v1 https://docengine.altura.bo/docs Servidor productivo de alta concurrencia.
Documentación Interactiva y OpenAPI Versionado
DocEngine expone la especificación OpenAPI v3 estándar en /openapi.json y provee interfaces interactivas para pruebas en /docs (Swagger UI) y /redoc (ReDoc). La especificación exportada se mantiene sincronizada y versionada en docs/openapi.json bajo la política de versionado docs/API_VERSIONING_POLICY.md.

3. Autenticación y Autorización (RBAC)

DocEngine implementa un esquema de seguridad basado en claves de API (X-API-Key) con control de acceso basado en roles (RBAC). El sistema puede operar en modo abierto (para redes internas/desarrollo local) o en modo autenticado estricto mediante la variable de entorno DOCENGINE_SECURITY_ENABLED=true.

Cabecera HTTP de Autenticación

X-API-Key: <TU_API_KEY_SECRETA>

Perfiles de Acceso (Roles)

Rol Permisos Otorgados Endpoints Habilitados
readonly Lectura y búsqueda POST /api/v1/query/search, POST /api/v1/query, GET /api/v1/policies/* (incluye datos estructurados), GET /api/v1/health/*.
writer Lectura + Ingesta documental Todos los permisos de readonly más POST /api/v1/extract/* y GET /api/v1/extract/jobs/*.
admin Control total Todos los permisos anteriores más DELETE /api/v1/policies/{policy_id} y DELETE /api/v1/policies/envelopes/{envelope_id}.

4. Convención Global de Errores y Respuestas

DocEngine se adhiere a las mejores prácticas de diseño RESTful y convenciones estándar de FastAPI/Starlette con esquemas de error estandarizados.

Estructura Estándar de Error JSON (ErrorDetailSchema)

{
  "detail": "Descripción precisa y legible del motivo del error o validación",
  "error_code": "INVALID_PAGE_COUNT",
  "timestamp": "2026-10-14T18:00:00Z"
}

Códigos de Estado HTTP Admitidos

Código HTTP Significado Contexto en DocEngine
200 OK Éxito síncrono La petición se procesó exitosamente y se retorna la información solicitada.
202 Accepted Procesamiento asíncrono La carga fue validada y puesta en cola en segundo plano; incluye job_id para consulta de estado.
400 Bad Request Petición inválida Parámetros incorrectos, archivo con formato no admitido (solo PDF) o archivo PDF corrupto/dañado.
401 Unauthorized No autenticado Falta la cabecera X-API-Key o la clave provista es inválida.
403 Forbidden Acceso denegado La clave tiene rol insuficiente para la operación solicitada (ej. rol readonly intentando eliminar).
404 Not Found No encontrado El sobre (envelope_id), documento (policy_id) o trabajo (job_id) no existe.
413 Content Too Large Archivo excedido El tamaño del archivo supera el límite configurado (por defecto 200 MB).
422 Unprocessable Content Validación / Límite páginas Error en formato de datos Pydantic o el PDF supera el límite máximo permitido de 500 páginas.
500 Internal Error Fallo de servidor Excepción no controlada en el motor de extracción Docling o en PostgreSQL.
503 Service Unavailable Servicio no disponible El motor vectorial o la base de datos se encuentran fuera de línea o en inicialización.

5. Paginación y Filtros Avanzados

Tanto los endpoints de búsqueda vectorial (/query/search) como los de gestión de sobres admiten filtros estructurados combinables mediante el objeto SearchFiltersSchema:

Filtro Tipo Descripción Ejemplo
id_cliente string Aislamiento multi-inquilino estricto por cliente. "CLI-001"
sigla_aseguradora string Sigla oficial normalizada contra el catálogo maestro (18 aseguradoras). "BISA", "CRI"
ramo string Ramo de seguro técnico normalizado. "AUTOMOTOR", "INCENDIO"
numero_poliza string Búsqueda exacta o parcial sobre el número de póliza. "POL-2024-9988"
tipo_documento string Tipo documental: POLIZA, CONDICIONADO_GENERAL, etc. "CONDICIONADO_GENERAL"
vigencia_fecha string (ISO) Filtra documentos cuya vigencia abarque la fecha especificada (YYYY-MM-DD). "2024-06-15"

6. Catálogo Detallado de Endpoints

6.1 Módulo de Ingesta y Extracción Documental (Extraction)

POST /api/v1/extract/file

Propósito: Carga un archivo PDF binario para extracción, chunking y vectorización. Soporta ejecución síncrona inmediata o asíncrona mediante el parámetro async_mode=true.

Content-Type: multipart/form-data

Campo Form Tipo Requerido Descripción
file Binary (PDF) Sí Archivo PDF (máximo 200 MB y 500 páginas).
id_cliente string No Identificador único del cliente para aislamiento multi-tenant.
company_sigla string No Sigla oficial de la aseguradora (ej. BISA, CRI, ALI).
numero_poliza string No Número de póliza para vinculación en sobre.
ramo string No Ramo de la póliza (ej. AUTOMOTOR).
tipo_documento string No Tipo de documento (ej. POLIZA, CONDICIONADO_GENERAL).
async_mode boolean No (def: false) Si es true, encola la tarea en background y retorna 202 Accepted con un job_id.

Respuesta Asíncrona (202 Accepted):

{
  "job_id": "d8e3b1c4-9a1f-4b12-a7e8-c51d9e2a4f00",
  "status": "PENDING",
  "message": "Extracción iniciada en segundo plano...",
  "check_status_url": "/api/v1/extract/jobs/d8e3b1c4-9a1f-4b12-a7e8-c51d9e2a4f00"
}

Propósito: Elimina un documento individual suelto (por ejemplo, para reemplazar un anexo o condicionado erróneo sin eliminar la póliza completa). Desvincula el documento del sobre, elimina sus fragmentos vectoriales en cascada y limpia los archivos derivados en disco.

Parámetro Path: policy_id (string, UUID del documento a eliminar).

Propósito: Elimina de forma atómica y completa una póliza entera (sobre) y todos sus documentos asociados.

6.3 Módulo de Consultas Semánticas RAG (RAG Query)

POST /api/v1/query/search

Propósito: Endpoint de búsqueda pura que devuelve los fragmentos relevantes recuperados por similitud híbrida (denso + recíproco FTS) con sus metadatos y puntaje, sin generar respuesta con LLM. Permite que cada agente o sistema externo utilice su propio modelo de lenguaje para la síntesis.

Content-Type: application/json

Campo JSON Tipo Requerido Descripción
question string Sí Consulta o texto de búsqueda temática.
top_k integer No (def: 5) Cantidad de fragmentos a recuperar (1 a 50).
filters object No Filtros combinables: sigla_aseguradora, ramo, numero_poliza, tipo_documento, vigencia_fecha, id_cliente.

Ejemplo de Respuesta (200 OK):

{
  "chunks": [
    {
      "chunk_id": "a1b2c3d4-e5f6-7a8b-9c0d-1e2f3a4b5c6d",

      "score": 0.892,
      "policy_id": "POL-2024-9988",
      "page_number": 3,
      "metadata": {
        "aseguradora": "BISA",
        "ramo": "AUTOMOTOR",
        "tipo_documento": "POLIZA",
        "file_name": "caratula_bisa.pdf"

POST /api/v1/query

Propósito: Responde preguntas formuladas en lenguaje natural sobre las pólizas digitalizadas, sintetizando una respuesta fundamentada con citas textuales a partir de fragmentos semánticos recuperados en pgvector.

6.4 Módulo de Sistema y Monitoreo (System & Health)

GET /api/v1/health

Propósito: Verificación básica de latido del servicio (liveness check). Retorna {"status": "ok"}.

GET /api/v1/health/system

Propósito: Reporte técnico completo: versión de DocEngine, motor de extracción (Docling), conectividad a PostgreSQL y modelos cargados.

7. Límites Técnicos por Archivo y Rendimiento

Para garantizar la estabilidad del servidor y evitar el agotamiento de memoria por archivos anómalos o de volumen desmedido, DocEngine aplica controles deterministas al inicio de cada petición:

Parámetro Límite Máximo Respuesta de Error Comportamiento
Tamaño de Archivo 200 MB por archivo 413 Content Too Large Rechazo inmediato antes de lectura en memoria o procesamiento.
Cantidad de Páginas 500 páginas por archivo 422 Unprocessable Content Validación previa mediante inspección de metadatos de página.
Formato de Archivo Solo application/pdf 400 Bad Request Rechazo inmediato si la firma binaria de PDF no es válida.
Manejo de Documentos Extensos (ej. 2,300 Páginas)
Documentos que superen las 500 páginas deben segmentarse antes de la ingesta en fascículos lógicos (por ejemplo, carátula, condiciones particulares y anexos por separado), o procesarse mediante el flujo asíncrono configurando max_pages_per_file en PerformanceConfig para evitar timeouts en conexiones HTTP síncronas.

8. Procesamiento Asíncrono, Idempotencia y Condicionados Generales

Condicionados Generales Compartidos

En el mercado asegurador boliviano, un mismo condicionado general aplica frecuentemente a múltiples pólizas de un mismo ramo. DocEngine permite registrar el condicionado general una única vez con tipo_documento="CONDICIONADO_GENERAL". Los agentes y consultas RAG pueden recuperar fragmentos del condicionado general utilizando el filtro ramo sin necesidad de duplicar el documento ni los vectores en cada póliza.

Ciclo de Vida de los Trabajos (Jobs)

Estado Significado
PENDING Archivo recibido y validado; en cola de ejecución en segundo plano.
PROCESSING Extracción Docling, atomización de coberturas y vectorización BGE-M3 en curso.
COMPLETED Documento procesado, estructurado e indexado exitosamente en PostgreSQL.
FAILED Fallo controlado durante el pipeline; incluye traza legible en error_message.
Resumen de Integración para Desarrolladores
Flujo recomendado para agentes de IA y sistemas ERP:
  1. Para búsqueda de fragmentos con LLM propio: invocar POST /api/v1/query/search pasando los filtros requeridos.
  2. Para obtener coberturas y deducibles estructurados: invocar GET /api/v1/policies/{policy_id}/structured.
  3. Para cargar documentos extensos: enviar con POST /api/v1/extract/file?async_mode=true y monitorear con GET /api/v1/extract/jobs/{job_id}.
  4. Para reemplazar un documento suelto erróneo: eliminarlo con DELETE /api/v1/policies/{policy_id} y subir la versión corregida.
